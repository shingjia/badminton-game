# 會內賽場地數彈性支援 — 設計文件

日期：2026-08-24
狀態：已核准，待寫實作計畫

## 背景

`docs/superpowers/specs/2026-08-20-club-inter-group-schedule-design.md` 原本的範圍界定明確寫著：「只支援『場地數 = 同時對戰數（組數/2）+ 1』這一種場地/組數關係。場地不夠或多出兩個以上先不處理，遇到就報錯。」

使用者提出：4 組、但只有 2 個場地（同時對戰數，沒有多一個共用場地）的情境也要支援。

**這是對前述範圍界定的擴充，不是取代**——原本的「同時對戰數 + 1」還是要繼續支援。

## 設計

會內賽的場地數驗證從「只接受 = 同時對戰數 + 1」改成「接受 = 同時對戰數，或 = 同時對戰數 + 1」，其他都還是報錯（`court_count_mismatch`）。

**核心洞察**：`lib/club-schedule.ts` 的 `buildClubSchedule` 本來就會把每場比賽標記成 `courtSlot: 'primary' | 'shared'`（主場地 / 共用場地），這個演算法完全不用改。只有場地數剛好等於「同時對戰數」（沒有多的共用場地）時，`'shared'` 標記的比賽也跟著 `'primary'` 一起指派到配對自己的主場地——因為沒有多的場地可以挪去負載平衡，效果就是「整組配對從頭到尾都用自己的場地」，比原本 3 場地的情況更單純。

只需要改 `src/app/api/tournaments/[id]/matches/generate/route.ts` 的兩處：
1. 場地數驗證（`courts.length !== primaryCourtsNeeded + 1` → 也接受 `=== primaryCourtsNeeded`）。
2. `courtId` 指派邏輯（判斷有沒有共用場地可用，沒有的話 `'shared'` 也走 `courts[m.pairingIndexInWave].id`）。

**`lib/club-schedule.ts` 完全不用改**，已經測試過的排程演算法維持原樣。

## 範圍

- 只支援兩種場地/組數關係：`= 同時對戰數` 或 `= 同時對戰數 + 1`。多出兩個以上、或少於同時對戰數，還是報錯，不處理。
- 不影響友誼賽（友誼賽的場地分配走 `allocateCourts`，跟這次改動的程式碼區塊完全不相干）。

## 測試

這個專案的 API route 本來就沒有自動化整合測試（沒有 DB 層測試基礎設施），這次改動也不例外，靠人工驗證：4 組、2 場地跟 4 組、3 場地兩種情境都要各自測一次。
