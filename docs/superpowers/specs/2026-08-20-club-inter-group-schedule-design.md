# 會內賽「組跟組對戰」賽制 — 設計文件

日期：2026-08-20
狀態：已核准，待寫實作計畫

## 背景

現行會內賽（`Tournament.format = 'club'`）流程：分組後，每一組**內部**依等級切成 A/B 兩隊，隊內循環搭檔互打（`splitByLevel2` + `rotationSchedule`）。

新需求：分組得到的每一組（A、B、C、D…）就是一支完整隊伍，**直接跟其他組對戰**，不再組內互切。例如 4 組、每組 6 人、3 場地：A vs B、C vs D、A vs C、B vs D、A vs D、B vs C，共 6 個對戰，每個對戰 6 輪循環搭檔，共 36 場。

**這是完全取代**，不是新增選項——會內賽以後都用這個方式，`splitByLevel2` 那條路徑不再被呼叫（保留檔案與測試，不刪除，純粹沒人 import）。

## 範圍界定（明確不處理的情況）

- 只支援**偶數組數**（4、6、8…）。奇數組數（需要 bye）先不處理，遇到就報錯。
- 只支援「場地數 = 同時對戰數（組數/2）+ 1」這一種場地/組數關係。場地不夠或多出兩個以上先不處理，遇到就報錯。
- 不要求每組人數相同（`rotationSchedule` 本身就不要求兩隊人數相等於彼此以外的其他隊——但同一場對戰的兩隊人數必須相等，這是 `rotationSchedule` 既有的限制，不是這次新加的）。

## 演算法

### 1. 組跟組怎麼配對成幾輪

直接重用 `lib/algorithms/circle-method.ts` 的 `roundRobinPairs(groupIds)`——它本來就是為循環賽設計的，輸入隊伍 id 陣列，輸出「誰跟誰對戰、第幾輪」，偶數隊伍不需要 bye，不用改。

對 4 組（A,B,C,D）跑 `roundRobinPairs(['A','B','C','D'])`，會得到 3 輪、每輪 2 場配對，等同 A vs B / C vs D（第1輪）、A vs C / B vs D（第2輪）、A vs D / B vs C（第3輪）。組數 N 的話會是 N-1 輪、每輪 N/2 場配對。

### 2. 每個「組跟組對戰」內部怎麼排

直接重用 `lib/rotation.ts` 的 `rotationSchedule(groupA球員, groupB球員)`——輸入兩支隊伍依棒次排序的球員，輸出 n 場比賽（n = 每隊人數），循環搭檔。這個函式本來就是為這種「兩隊互打」場景設計的，不用改。

（`rotationSchedule` 內部算的 `roundNumber` 欄位，是給「同一個對戰內的比賽要不要衝突」用的——這次不需要，因為兩個同時進行的對戰之間完全沒有共用球員，怎麼排都不會衝突。這欄位還是會產生，但這次的場地分配邏輯不看它，只看比賽的先後順序（k）。）

### 3. 場地怎麼分配（新寫的部分）

每一輪（wave）有 N/2 個對戰、N/2+1 個場地。規則：

- 每輪內第 i 個對戰（照 `roundRobinPairs` 給的順序）固定用第 i 個場地當**主場地**——這個場地在每一輪都給「隊伍組合裡的第 i 個位置」用（例如場地1 永遠是每輪的第一個配對：A vs B → A vs C → A vs D）。
- 最後一個場地（第 N/2+1 個）當**共用場地**，服務所有輪次、所有對戰溢出的比賽。
- 每個對戰共 n 場比賽（n = 每隊人數），主場地留 `x` 場、共用場地拉 `n - x` 場：

  ```
  x = round(N × n / (N + 2))，並夾在 [0, n] 範圍內
  ```

  以 4 組、每隊 6 人為例：x = round(24/6) = 4，主場地留前 4 場（k=0..3），共用場地拉最後 2 場（k=4,5）。這樣每一輪的三個場地都剛好各 4 場（主場地 4、主場地 4、共用場地 2+2=4），完全均衡。
- 主場地上的比賽照 k 由小到大排；共用場地上，同一輪兩個對戰溢出的比賽交錯放（第一個對戰的溢出、第二個對戰的溢出、第一個對戰的溢出…），避免同一對戰的兩場溢出比賽黏在一起。

### 4. Match / Pair 怎麼寫進資料庫

沿用現有的「一場比賽建兩個一次性 Pair」模式（跟現在會內賽一樣，`Pair.groupId` 分別存這一邊隊伍所屬的組）。

**`Match.groupId` 這個欄位**：資料庫要求不可為空，但一場比賽現在橫跨兩個組，沒有真正對應的單一組。做法：固定存 pairA 那一組的 id（純技術性欄位，沒有語意上的意義，UI 不應該只靠這個欄位判斷「這場比賽屬於哪組」）。

## 排名計算要修正（設計階段發現的既有 bug）

`lib/player-standings.ts` 的 `computePlayerStandings` 目前用 `MatchResult.groupId`（也就是 `Match.groupId`）把兩邊球員的戰績都歸到同一組——這在舊模型（比賽只在組內發生）是對的，但新模型下 pairA、pairB 屬於不同組，會把 B 組贏的場次誤算進 A 組。

**修正**：`MatchResult` 拿掉單一的 `groupId`，改成 `pairAGroupId` / `pairBGroupId` 兩個欄位，`computePlayerStandings` 的 `tally()` 呼叫時，A 側球員用 `pairAGroupId`、B 側球員用 `pairBGroupId`，不要共用同一個值。`computeGroupStandings`（組跟組排名，上一輪剛做的功能）不用改，它本來就是把 `computePlayerStandings` 的結果依 `groupId` 加總，只要輸入的 `groupId` 正確，加總邏輯不變。

友誼賽那條路徑（`getStandings`／`pair_standings` SQL view）完全不受影響，繼續用 Pair 本身的 groupId，沒有這個問題（友誼賽的 Pair 本來就只屬於一個組）。

## Viewer 顯示要修正

`matches-tab.tsx` 的「分組列表」檢視目前用 `m.group.name` 把比賽分類顯示。新模型下這樣會很奇怪（A vs B 的比賽只會出現在「A組」底下，看不出對手是誰）。

改成依「對戰配對」分類——用 `pairA` 所屬球員的組名 + `pairB` 所屬球員的組名組成「A vs B」這種標題，取代原本的「A 組」標題。「場地列表」檢視不受影響（本來就是照場地分，不是照組分）。

`groups-tab.tsx`、`section-groups.tsx`（admin 分組頁）不受影響——分組階段的行為完全沒變，只有分組**之後**「怎麼產生賽程」的邏輯換了。

## 已知的簡化 / 之後可以再加

- 奇數組數、場地數不是「同時對戰數+1」的情況，先報錯，不處理。
- 主場地/共用場地的比賽數用四捨五入公式算，極端人數比例下可能不是完全均衡（例如四捨五入後某場地多一場），這是已知的近似，不追求數學上絕對公平。
- `splitByLevel2` 保留在 `lib/rotation.ts`，不刪除，純粹沒有呼叫者。

## 測試

- 新的場地分配計算（x 公式、共用場地交錯排列）：至少涵蓋設計文件裡 4組/6人/3場地 這個具體案例，驗證三個場地都恰好 4 場。
- `computePlayerStandings` 修正後：涵蓋「A組球員贏了對 B 組的比賽，戰績只算進 A 組、不會污染 B 組」這個案例（這正是這次修正要解決的 bug）。
